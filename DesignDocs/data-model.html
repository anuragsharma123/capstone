The lowest-level Postgres schema — how tenancy, agent versions, paused graph runs and the admin review queue are laid out, and why the queue that worries you about admin overload stays in a relational database.

"Admin gets bombarded" is a workflow problem, not a storage one. Submissions are human-triggered — someone clicks Publish — so even a large org produces ~10³ a day; with a three-day SLA the pending set is a few thousand rows. A partial index scans that in microseconds. Moving it to NoSQL would cost you two grading checks, not buy you scale.

Isolation is RLS (Check 1)

Tenant + user isolation is a Postgres row-security policy, not an app filter. Delete every WHERE owner_id = ? in the code and the database still returns only your rows — see Row-level security.

Decide + resume is atomic (Checks 5, 6)

"Approve" must record the decision and schedule the run's resume in one transaction. Two datastores means a dual-write and a new failure mode: approved but never resumed.

The audit trail is relational

Who approved what, when, with what notes — a compliance artifact that wants to be queried and joined to users.

You still get schemaless where it helps

jsonb columns hold the loose-shaped parts — the config document, the sanitized manifest, score breakdowns, LangGraph's checkpoint blobs — inside the same database.

/Row-level security — in plain terms

The structural half of Rule 2. Instead of every query remembering WHERE owner_id = ?, PostgreSQL attaches the filter to the table itself and applies it to every statement — so there is no filter to forget.

A policy is a per-row test. It is a boolean expression the database evaluates for each row. Rows where it is false are not "access denied" — they are simply invisible: they don't come back from a SELECT, an UPDATE or DELETE can't touch them, and WITH CHECK stops an INSERT from writing a row that wouldn't be yours.

The policy on every user-owned table

alter table agents enable row level security;
alter table agents force  row level security;   -- applies even to the role that owns the table

create policy owner_isolation on agents
  using      (owner_id  = current_setting('app.user_id')::uuid
          and tenant_id = current_setting('app.tenant_id')::uuid)   -- second barrier
  with check (owner_id  = current_setting('app.user_id')::uuid
          and tenant_id = current_setting('app.tenant_id')::uuid);

-- the app connects as this role — NOT a superuser (superusers ignore every policy)
create role app_runtime nologin;
grant select, insert, update, delete on agents to app_runtime;

The same policy sits on every user-owned table — mcp_servers, mcp_tools, connections, agents, agent_versions, graph_runs. Each carries a denormalized owner_id + tenant_id so the test is a local column compare — no join. users is keyed on tenant_id (you see your own colleagues); tenants is the root and has neither.

What the app supplies — once per request, inside the transaction

-- values taken from the verified JWT, never from a query parameter
set local app.tenant_id = '…';   -- SET LOCAL: this transaction only, cleared on commit
set local app.user_id   = '…';   -- so a pooled connection never carries the last request's identity

What PostgreSQL actually runs

-- your code
select * from agents;

-- what executes
select * from agents
where owner_id = :app_user_id and tenant_id = :app_tenant_id;

Two teammates in the same company run identical SQL and get different rows. The application never writes that WHERE clause.

Why owner_id, not just tenant_id. Rule 2 says "my agents, my connections, my runs — mine. Nobody else," and grading check 1 is user-to-user. A tenant-only policy would let a colleague read your agents the moment the app-level filter is removed. tenant_id stays in the policy as a second barrier, and in the schema for the marketplace, install, admin review and billing.

What breaks it — and how we avoid it

App runs as a superuser

Superusers and any role with BYPASSRLS ignore every policy. The request-serving role must be a plain app_runtime; migrations use a separate privileged role.

FORCE left off

By default the role that owns a table is exempt from its own policies. alter table … force row level security closes that.

SET instead of SET LOCAL

With connection pooling a plain SET outlives the request; the next caller on that connection inherits the previous user's identity. SET LOCAL is transaction-scoped.

Setting left unset

Read it as current_setting('app.user_id', true) → returns NULL when missing → the policy matches nothing. Fail closed, never "match every row".

The one exception

marketplace, review_submissions and resume_outbox have RLS not enabled, and are granted only to a separate app_reviewer role. The cross-tenant read is deliberate and lives in the grant — not in a WHERE clause someone could forget.

How check 1 runs against it

The graders delete your application-level filter and query another user's agent by id. Under the policy that query returns zero rows — so the endpoint answers 404, never 403 (a 403 would confirm the agent exists).

/Draining the queue under load

The two patterns that make "bombarded admin" a non-event — both plain Postgres.

Concurrent admins pull work without colliding. FOR UPDATE SKIP LOCKED is the canonical work-queue pattern: N admins call this at once, each gets a different row, nobody blocks.

update review_submissions s
set    status = 'in_review', claimed_by = $admin_id, claimed_at = now()
from (
  select id
  from   review_submissions
  where  status = 'pending'
  order  by priority, submitted_at
  for update skip locked
  limit  1
) nxt
where s.id = nxt.id
returning s.*;

Decide and schedule the resume in one transaction. This is the guarantee you would lose the moment the queue lived in a different datastore.

begin;

update review_submissions
set    status = 'approved', decided_by = $admin_id, decided_at = now(),
       decision_notes = $notes
where  id = $id and status = 'in_review';

insert into resume_outbox (graph_run_id, resume_value)
select graph_run_id, '{"approved": true}'::jsonb
from   review_submissions
where  id = $id;

commit;
-- a worker: select ... from resume_outbox where processed_at is null
--           for update skip locked;
--           graph.invoke(Command(resume=v), {"configurable": {"thread_id": run.thread_id}})

Everything that absorbs the load is already in the model: the partial index keeps the pending scan tiny, SKIP LOCKED lets admins parallelize, the partial unique index stops resubmits piling up, Rule 6 keeps sub-threshold agents out of the queue entirely, and priority gives you a fast lane. If dispatch ever outgrows one Postgres — it won't, at this scale — move the work signal to pgmq or Redis Streams and keep the records and the audit trail here. The schema above doesn't change.
