Platform Architecture

A high-level design for the thing that builds agents — how a plain-English description becomes a deployed, publishable, multi-tenant agent, and how each of the eight rules is made true by structure rather than discipline.

The platform is a build pipeline and a runtime sharing one multi-tenant datastore. An agent is never generated code — it is a configuration document the runtime assembles. And every place the process waits for a human is a durable graph pause, so a build or an approval can sit for days across redeploys and still resume exactly where it stopped.

/System overview

Four planes: clients, an authenticating edge, the platform services, and one Postgres instance that both enforces isolation and stores durable graph state.

/The six-step flow

The demo walks this path end to end without cuts. Numbered because it is a genuine sequence — each step depends on the one before it.

  1. Register a tool server

    Paste an MCP server address and save. The platform connects, asks the server what tools it has, and stores the answer with each tool marked read, write, or destructive. No tool names are typed by hand.

  2. Connect to it

    Paste your token once. It is encrypted on arrival. You never see it again, and nothing in the system reads it that does not strictly need it. Every agent you build reuses this connection.

  3. Describe an agent

    Type the goal in plain English. The platform proposes servers from the registry — you tick the ones you want — then checks each connection and stops if one is missing. It builds, deploys, and shows the name, description, capabilities and score. Those two stops are LangGraph interrupts and survive a server restart.

  4. Test it

    The agent appears in My Agents as a card. Its page has the graph, tools, scores, run history and API endpoint. A playground chat runs it — and when it tries something risky it stops and asks you to Approve or Reject right in the chat.

  5. Publish it

    Publish to Marketplace does not go live — it goes to an admin, who sees what the agent does and how it scored, and either approves it or sends it back with notes. That review may sit for three days across two deploys and a weekend; answering resumes the run.

  6. Someone else installs it

    A person in a different company opens the Marketplace, clicks Add to my workspace, and gets their own copy. They supply their own credentials. They never touch the original, and the original owner's tokens never move.

/Rules → mechanism

How each of the eight rules is satisfied — and where in the system it is enforced.

RuleWhere it livesMechanism
Rule 1Configuration, not code Config Store + Runtime Build emits a versioned config document; one runtime interprets it. No code generation, no per-agent Python. This is the decision everything else hangs off — versioning, safety, and portability into another workspace.
Rule 2Tenant isolation Postgres RLS + tenant-context middleware Auth stamps tenant_id into the JWT; middleware sets it as a DB session variable per request; RLS policies filter every table. Remove the app-level filter and isolation still holds. The marketplace and review tables carry no RLS policy — the one deliberate exception, visible to any authenticated user but sanitized.
Rule 3Credentials vanish Credential Vault + KMS Envelope-encrypted on write, ciphertext-only column. The runtime does fetch → use → drop. A token never lands in a config, a prompt, a log, or a saved conversation.
Rule 4Risky actions ask first Approval Gate in the runtime The gate keys off the tool's read/write/destructive tag from the registry — not the agent's prompt. Any write or delete pauses as an interrupt until a person approves.
Rule 5Publishing strips the company Sanitizer What reaches the Marketplace is the design only — what it does and which kinds of access it needs. Owner, credentials and internal text are dropped. Tested against planted confidential material.
Rule 6Scores must mean something Scoring Engine Deterministic rubric for effectiveness and safety — every number traceable to a rule, no model guessing. Publish is disabled below threshold and says why.
Rule 7Every agent gets an endpoint Gateway → Runtime Per-agent URL plus a downloadable Postman collection on the agent page. A token from another company gets 404, not 403 — under RLS the row is invisible, so the platform cannot even confirm the agent exists.
Rule 8One real multi-agent system Config schema + Runtime The config supports a coordinator delegating to ≥2 specialists with a human approval step between. The demo agent is built through the platform, not hand-written.

/Surviving restarts & long waits

Grading checks 5 and 6: killing the server mid-build must resume correctly, and an approval left pending overnight must still resume the next day. Both are the same mechanism.

/Decisions still open

The parts that need a design pass before implementation starts.

The agent config document schema

The central design problem. It must carry identity, graph shape (nodes, edges, sub-agents), tool references by capability, not by credential, interrupt points, prompt templates, the inputs its scores are computed from, and a version — and stay portable into another tenant.

The build graph's interrupt points

Exactly where the orchestrator pauses (server selection, missing connection), what state each checkpoint carries, and how a resumed run reconciles with a registry or connection that changed while it was paused.

Isolation mechanics

The RLS policy shape, how the middleware sets and clears the session variable per request, and what that means for connection pooling and the background runtime workers.

The scoring rubric

The actual formulas for effectiveness and safety, the thresholds that block publication, and how each contributing factor is surfaced so a number can always be explained.
