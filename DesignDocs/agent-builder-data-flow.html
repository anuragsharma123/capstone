/How a pause works

The reason the build can stop for days and resume exactly where it was (grading check 5).

  1. At present_tools / request_credentials the graph calls LangGraph's interrupt().

  2. The graph's full state is written to the checkpointer (Postgres), keyed by thread_id.

  3. The graph_runs row is updated → status='interrupted', interrupt_kind='select_servers' | 'add_connection', interrupt_payload = what the UI should render.

  4. The HTTP request returns. Nothing stays in server memory.

  5. Later: POST /builder/{thread_id}/resume { … } → the graph loads its state from the checkpointer and continues from the exact node it stopped at.

Why it survives a restart

The paused state lives in Postgres, not in the process. Kill the server during PAUSE 1, redeploy, then submit the tool picks — resume reloads the state and the build continues.

Update — 2026-09-12: Admin Review turned out not to use this same mechanism — see Publish → Review → Marketplace below for why.

/generate_config — where "agent = data" becomes real

Rule 1. The output is one JSON document → a new agent_versions row. It is never generated code.

{
  "schema_version": "1.0",
  "name": "GitHub Issues → Slack Summary",
  "model": "claude-sonnet-5",
  "system_prompt": "List open GitHub issues assigned to the user, summarize them, post to #standup.",
  "graph": { "type": "sequential" },
  "tools": [
    { "mcp_server_id": "uuid-github", "tool_name": "list_issues",  "sensitivity": "read",  "require_approval": false },
    { "mcp_server_id": "uuid-slack",  "tool_name": "post_message", "sensitivity": "write", "require_approval": true }
  ],
  "interrupt_before": ["post_message"]
}

  1. Portable. Tools reference mcp_server_id + capability, never a credential. The same document installs into another tenant who brings their own connection; the runtime resolves mcp_server_id → the caller's connection at run time.

  2. Versioned. Every build or later edit is a new agent_versions row — never mutated in place.

  3. Safe by construction. The gate (interrupt_before) is derived from the DB's sensitivity marking, so a model can't talk its way past it and neither can a hand-edited prompt.

The result

Effectiveness 55 is below 60 → Publish disabled, reason shown: "add a schedule or a fuller prompt."

Remove post_message from interrupt_before → write-gated becomes 0 → safety 35 → still can't publish. That's grading check 3.

Every sub-score is stored, so "why 75?" answers itself: 40 + 10 + 20 + 5. No LLM, ever — same config, same score.

/Publish → Review → Marketplace

Rule 5 (publishing strips the company) and Rule 6's other half — the score gate is score_agent's (above) use, this is what happens after it passes. Built and verified 2026-09-12: a real 55/100 agent blocked, a real 69/100 agent published, and a rejection sent an agent back to draft.

code decides: score, gate, sanitize human decides: approve / request changes / reject

  1. Owner asks to publish an existing agent_versions row (already status='draft' — the build finished long before this, possibly days earlier).

  2. score_agent's logic runs (above). If effectiveness < 60 or safety < 70, publish is rejected right here with the reason; nothing is written.

  3. If it clears the gate: agent_versions — UPDATE effectiveness_score, safety_score, score_breakdown, status='in_review'.

  4. The Sanitizer strips the config to a manifest: name, description, model, graph.type, and each tool's {name, sensitivity} — never mcp_server_id, never system_prompt (where planted confidential material would live, Rule 5's actual test).

  5. review_submissions — INSERT {sanitized_manifest, effectiveness_score, safety_score, score_breakdown, status: 'pending', priority}. Any destructive capability bumps priority to the front of the queue.

  6. An admin lists the pending queue and decides: approved · changes_requested · rejected.

  7. Approved → marketplace — INSERT the same sanitized manifest + scores, denormalized (a listing read never touches a tenant-scoped table) · agent_versions.status='published'.

  8. Changes requested / rejected → agent_versions.status='draft' — back to the owner, with decision_notes explaining why. Nothing reaches marketplace.

Why this isn't a build-graph pause

"How a pause works" above established pauses as "full state to the checkpointer, graph_runs.status='interrupted', resume reloads and continues." Admin Review looks like it should be the same mechanism — await_approval is even a valid interrupt_kind in the schema — but it isn't, here.

By the time an owner asks to publish, the build graph's thread already reached END; the config is fully persisted. There's no live thread to pause or resume — publish just reads that finished row, and admin approval writes directly, with no outbox and no worker re-invoking a graph. This only holds because generate_config and score_agent are plain functions here, not graph nodes gated by this pause — see DESIGN-NOTES §2.14 for the full reasoning and what would change it.

Not built: Install. "Independent copy, installer supplies own creds" needs a second identity to mean anything — there is exactly one hardcoded owner in this whole prototype today.

/Never in the config

Rule 3 · Rule 5 — checked against the stored config

The Build Orchestrator never reads a credential and never writes one. agent_versions.config references servers by mcp_server_id only. No token, no tenant_id in the document body, no company text — the same row is what the Sanitizer reads on publish (above), so anything tenant-specific in it would be a leak. Verified 2026-09-12: a real published manifest carries only name/description/model/graphType/capabilities — no mcp_server_id, no system_prompt.
