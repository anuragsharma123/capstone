MCP Server, Tools & Connection — Data Flow

How a registered server becomes something an agent can safely use: discover the tools and classify each one read / write / destructive; define an auth_spec and render a form from it; then envelope-encrypt the secret so it is fetched, used, and dropped — and written nowhere else.

/Tool type — read / write / destructive

The value on mcp_tools.sensitivity is computed by the platform at discovery (step 6), conservatively, and a tenant can never lower it. It is the single input the approval gate reads.

read — no change to the outside world write — creates or modifies destructive — deletes or is irreversible

classify(server, tool) — highest priority first:

  1  override catalog   (server, tool) pinned by a platform admin         → use it
  2  MCP annotations    destructiveHint == true                            → destructive
                     readOnlyHint    == true                            → read
                     readOnlyHint    == false                           → write
  3  name / description  /delete|remove|drop|purge|revoke|wipe|merge/     → destructive
                      /create|update|post|send|add|set|write|patch/     → write
                      /list|get|search|read|fetch|query|describe/       → read
  4  no confident match                                                  → write   (fail-safe — never 'read')

  1. Stored on mcp_tools: sensitivity (the final call), sensitivity_source (override | annotation | heuristic | default), annotations jsonb (the raw hints, kept for audit). So you can always show why a tool is marked the way it is.

  2. MCP annotations are hints, not truth. The MCP spec says clients must not rely on readOnlyHint / destructiveHint for security. They are used only when they make a tool more restrictive; otherwise the heuristic runs; unknown falls to write.

  3. The tenant cannot dial it down. At registration the classified list is shown read-only. Only a platform admin overrides — via the global tool_classification_overrides catalog (server pattern, tool, sensitivity, reason, set_by), which is audited and wins as priority 1. If a tenant could mark everything read, Rule 4 is bypassed.

  4. How it enforces the gate — three points, not one:

StageWhat it does with sensitivity
BuildAny write / destructive tool → require_approval = true is written into the config. A config that sets it false on such a tool is rejected.
RuntimeBefore every tool call the runtime re-reads mcp_tools.sensitivity from the DB. write / destructive → LangGraph interrupt — regardless of the config flag or the prompt. This is the check that survives "delete the app-level filter".
PublishA write / destructive tool with no approval gate drives the safety score below threshold → Publish disabled (grading check 3).

On re-introspection: if a server changes and a tool shifts read → write, every agent version using it is re-scored and flagged; if it drops below the threshold it can't be re-published until its config adds the gate.

/The auth_spec field

A JSONB column on mcp_servers. It is the contract between the server and the Connections form — and between the form and the Vault.

{
  "type": "bearer",        // bearer | header | basic | query — how the secret attaches to MCP calls
  "fields": [
    {
      "key": "token",
      "label": "GitHub personal access token",
      "help": "Needs 'repo' scope — github.com/settings/tokens",
      "secret": true          // secret:true → encrypted;  secret:false → stored as plain config
    }
  ],
  "headerName": null,        // required when type is "header" — the header name itself
  "queryParam": null         // required when type is "query" — the URL param name
}

  1. Render the form. Step 9 hands fields[] to the UI. One field for GitHub or Slack; two for basic; a server that needs an org name or base URL alongside the token lists those as extra fields with secret:false.

  2. Split on save. Step 11 sends only secret:true values to the Vault → connections.ciphertext. Non-secret values go to a plain connections.config jsonb — useful, not sensitive, never encrypted.

  3. Verify. No separate test call — the Registry Service re-runs the same tools/list discovery call from Phase 1, now with the submitted credential attached per type. Success → store and return connected: true; failure → 400, nothing is written. One mechanism serves both discovery and verification instead of a second server-specific concept.

  4. Attach at call time. Step 20 uses type to decide: bearer → Authorization: Bearer, header → the named header from headerName, basic → a Base64 Authorization: Basic of the first two fields, query → a URL param named by queryParam.

Where it comes from: always the registrant, on the Register form, at registration time — never captured from the server. Real MCP servers don't advertise this in tools/list, so the "if advertised, capture it" path was dropped rather than built as dead code (DESIGN-NOTES §2.7 addendum). The platform then treats auth_spec as read-only.

/How the secret is stored — two locks, not one

This is envelope encryption. The token goes behind two keys, and the database only ever holds the locked versions (steps 11–14).

connections row
  ciphertext    = token  encrypted with a fresh per-connection Data Encryption Key (DEK)
  wrapped_dek   = that DEK encrypted with the KMS master key   (master key never leaves the KMS)
  nonce, key_version                                      metadata — not secret
  — never stored: plaintext token · plaintext DEK · master key

To recover the token you need both the row and the right to call the KMS. A stolen database dump on its own is inert — every field in it is already encrypted.

Why two layersWhat it buys you
Blast radiusDB compromise ≠ key compromise. The KMS is the trust boundary; the master key is never in the app or the DB.
Key rotationRotate the master key by re-wrapping the small DEKs — you never re-encrypt every stored token.
Least useThe master key only ever encrypts tiny keys, not payloads — minimal exposure, fits KMS rate limits.
AuditThe KMS logs every unwrap: "credential X decrypted at time T" — an access trail a plain column can't give you.

Reverse path (steps 17–18): read row → KMS unwraps wrapped_dek → plaintext DEK → decrypt ciphertext → token in memory → one call → drop DEK + token.

Update — 2026-09-12: this reverse path now has its first real caller: the scheduled liveness check (health.ts → getConnectionAuth()) runs it once per tick against every connected server. Two side effects land on the connections row every time: last_used_at is stamped, and status is set from the result — a 401/403 back means the token itself was rejected, so status flips to expired (the server stays mcp_servers.status = 'ok', since it clearly responded); anything else that succeeds sets it back to active. Same reverse path an actual tool call will use once the Run lane exists — this is that pattern's first exercise, not a second one.

For the capstone — no paid KMS

The "KMS" is a single master key in an env var (or a key file); wrap / unwrap is a small function — e.g. Fernet for the inner layer, Fernet-with-the-master-key for wrapping the DEK. Same shape, same guarantees, runs in docker compose.

/What the task fixes vs. what we chose

Rule 3 and Step 2 define an outcome. Every mechanism below it is our design decision — the task says so: "how you satisfy them is your design decision."

The task fixes (Rule 3 + Step 2)We chose
"it is encrypted immediately"Envelope encryption — a fresh per-connection DEK, AEAD, KMS-wrapped key
"fetch it, use it, drop it"A "Credential Vault" module owns that lifecycle; decrypt in memory only, never cached
never in config / prompt / log / conversationThe agent config references server_id by capability — the value is never in it
"we search everything you stored… finding it is a fail"Only ciphertext + wrapped_dek are ever persisted
"nothing that does not strictly need it"KMS master-key boundary; per-unwrap audit log; least-access reads scoped by RLS
tools marked read / write / destructiveThe classify() pipeline, the fail-safe default, the platform-only override catalog

The floor

The minimum that passes Rule 3's grep test: one symmetric key (a single Fernet key in an env var) doing authenticated encryption on the token column, plus disciplined fetch→use→drop. Envelope encryption + a KMS boundary is a strengthening — rotation, blast radius, audit — not a task requirement. "Vault" is our name for the module, not a mandate to run HashiCorp Vault.

/Where the secret must never appear

Grep target — finding it anywhere is a fail

The plaintext credential exists only in transit (step 10, TLS) and briefly in Vault memory (steps 11, 18). It is never written to agent_versions.config, request/response logs, the LangGraph checkpoint tables, saved playground transcripts, or any API response body. The auth_spec and the tool sensitivity are safe to expose freely — they are metadata, not values.
